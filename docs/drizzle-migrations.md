# D1 migrations with Drizzle

The app's database is Cloudflare D1 (SQLite), owned by `packages/db`. Migrations
are generated by drizzle-kit, flattened into wrangler's layout, checked in, and
applied with `wrangler d1 migrations apply`. They are **forward-only** and
**expand/contract only**; the reasons are below and enforced by tests and
`pnpm check:standards`.

## Quick reference

```bash
pnpm db:generate          # drizzle-kit generate + flatten → packages/db/{drizzle,migrations}
pnpm db:migrate:local     # wrangler d1 migrations apply DB --local   (Miniflare, .wrangler/state)
pnpm db:migrate:remote    # wrangler d1 migrations apply DB --remote  (the stage's database)
pnpm db:check             # drizzle-kit check: snapshots in drizzle/ are consistent
pnpm db:seed              # seed:sql + wrangler d1 execute --local --file seed/seed.sql
pnpm db:studio            # drizzle-kit studio over the d1-http driver (needs the CF credentials)
pnpm db:rehearse:remote   # migrate:remote against the local D1 emulator (no CF account)
pnpm -F @gmacko/db test:workers   # the migration set + Database suite on a real (Miniflare) D1
```

Binding and paths come from `apps/web/wrangler.jsonc` (`d1_databases[].binding
= "DB"`, `migrations_dir = ../../packages/db/migrations`). drizzle-kit reads
`packages/db/drizzle.config.ts` (`dialect: "sqlite"`, `driver: "d1-http"`,
`schema: ./src/schema.ts`, `out: ./drizzle`).

## Workflow: generate → flatten → apply

1. **Edit the schema** in `packages/db/src/schema.ts` (or `auth-schema.ts`,
   hand-maintained against better-auth's CLI output). Use the helpers in `columns.ts` (`id`,
   `timestampMs`, `bool`, `json`, `timestamps`) so every table maps to SQLite the
   same way; column names are explicit snake_case because the Effect D1 driver
   ignores `casing`.

2. **Generate**: `pnpm db:generate`.
   - drizzle-kit writes `packages/db/drizzle/<YYYYMMDDHHmmss>_<slug>/{migration.sql,snapshot.json}`
     (the 1.0 layout: one folder per migration, no `meta/_journal.json`).
   - `scripts/flatten-migrations.mjs` copies each `migration.sql` to
     `packages/db/migrations/<YYYYMMDDHHmmss>_<slug>.sql`, which is what
     `wrangler d1 migrations apply` and `readD1Migrations` want, and removes flat
     files whose folder is gone. Both directories are committed: `drizzle/` is
     drizzle-kit's source of truth (snapshots for diffing), `migrations/` is what
     D1 applies. Never hand-edit one without the other.

3. **Inspect the SQL before committing.** Open the new `migration.sql` and
   check:
   - no `__new_` table and no `PRAGMA foreign_keys=OFF` (see the rule below;
     `pnpm check:standards` fails on either);
   - every `ADD COLUMN` is nullable or has a `DEFAULT` (a `NOT NULL` add without a
     default fails on any table with rows, which is why
     `20260903035551_auth_1_7_issuer.sql` is empty-database-only);
   - statements are separated by `--> statement-breakpoint` (the Node test layer
     refuses a chunk holding two statements; wrangler splits on `;`).

4. **Apply locally and run the suites**: `pnpm db:migrate:local`, then
   `pnpm -F @gmacko/db test` and `pnpm -F @gmacko/db test:workers`. The Workers
   suite applies the whole set to an empty Miniflare D1 exactly the way wrangler
   does (each file as one batch) and asserts no `__new_` table survives.

5. **Apply remotely as part of the deploy**: `pnpm db:migrate:remote` runs
   before `wrangler deploy` in the same stage; a failed migration aborts the
   deploy. Migrations are recorded in the `d1_migrations` table, so re-running
   `apply` is a no-op for files already applied.

## Rehearsing a remote migration

`migrate:remote`, `seed:remote`, `reset:remote` and `wrangler d1 create` all
talk to Cloudflare's REST API, so until recently none of them could be run
without an account — the paths that touch a *production* database were the
only paths with no local rehearsal. `@gmacko/emulate` 0.11 ships a Cloudflare
D1 + R2 emulator backed by Miniflare, which is workerd's SQLite: the same
engine production D1 runs on, quirks included.

One variable redirects wrangler. **It must end in `/client/v4`** — that is the
only prefix `api.cloudflare.com` serves, and the emulator serves nothing else,
on purpose:

```bash
npx @gmacko/emulate start --service cloudflare --port 4111 &

export CLOUDFLARE_API_BASE_URL="http://127.0.0.1:4111/client/v4"
export CLOUDFLARE_ACCOUNT_ID="d1-rehearsal"       # any string; the emulator namespaces by it
export CLOUDFLARE_API_TOKEN="d1-rehearsal-token"  # any string; nothing is checked

cd packages/db
pnpm exec wrangler d1 create d1-rehearsal
pnpm exec wrangler d1 migrations apply DB --remote --config <config pointing at that database>
pnpm exec wrangler d1 execute DB --remote --command "select count(*) from d1_migrations"
```

Drop the `/client/v4` and every call fails with Cloudflare's own envelope —
`code: 7003, "Could not route to …"` plus a second error naming the missing
prefix — rather than quietly working against a different route shape.

`pnpm db:rehearse:remote` (`scripts/d1-remote-rehearsal.mjs`) is that sequence
wired up: it starts the emulator, creates a throwaway database, writes a
temporary wrangler config (the committed one points `database_id` at a
placeholder uuid the emulator has never seen), applies the whole migration set
through `--remote`, and then asserts that

- `d1_migrations` records every file in `packages/db/migrations`,
- no `__new_<table>` survived (the rebuild recipe below),
- re-applying is a no-op, which is what makes a failed deploy safe to retry.

CI runs it on every PR (`.github/workflows/ci.yml`, the
`D1 Remote Migration Rehearsal` job). It is **not** a second copy of
`pnpm -F @gmacko/db test:workers`: that suite applies the files the way *local*
wrangler does — wrangler reads each file, splits it on `;` and sends the
statements itself. `--remote` POSTs the file's SQL to the D1 HTTP API, which
splits it server side and runs the result as one atomic batch. Different
execution path, and it is the one a deploy uses.

### What the rehearsal does not cover

- **`seed:remote` and `reset:remote`.** Both are
  `wrangler d1 execute --remote --file`, which uses Cloudflare's four-phase
  import protocol; the emulator answers that with an explicit
  `not implemented` envelope (`code: 7500`). `--remote --command` works, and is
  what the assertions use. The seed and reset SQL are exercised against the
  local database (`pnpm db:seed`) instead.
- **drizzle-kit against the emulator.** The `d1-http` driver hardcodes
  `https://api.cloudflare.com` with no base-URL override, so
  `drizzle-kit push`/`migrate`/`studio`/`introspect` cannot be pointed at it.
  That is why the supported path is `drizzle-kit generate` (offline) plus
  `wrangler d1 migrations apply` — what `pnpm db:generate` and this rehearsal
  do — and why `db:studio` still needs real credentials.
- **Time Travel, `d1 export`, `d1 import`.** Not implemented by the emulator;
  they answer with an explanatory `success: false` envelope.

## Forward-only, expand/contract

There is no "down" migration. Rollback is either a new forward migration or a
Time Travel restore (below). Because the code that is live during a deploy may
be either the old or the new version for a while, a release may only:

- **add** columns (nullable or defaulted), tables, and indexes;
- **backfill** in the app or in a follow-up migration;
- **tighten** (make a column required) only at the application boundary — SQLite
  has no `ALTER COLUMN`, so a database-level `NOT NULL` on an existing column is
  a table rebuild, which D1 forbids for any table something references (next
  section). Enforce it in the domain `Schema` and keep the column nullable in
  DDL, or, for a table with no `ON DELETE CASCADE` targets pointing at it, do
  new-table-and-copy across two releases;
- **drop or rename** a column or table only in the release *after* no deployed
  code references it.

### The D1 rule: never rebuild a table

D1 runs each migration file as a single batch (one transaction) and **ignores
`PRAGMA foreign_keys=OFF` inside it** — `PRAGMA foreign_keys` still reads `1`.
drizzle-kit's SQLite recipe for anything it cannot express as an `ALTER`
(dropping a constraint, changing a type, adding `NOT NULL`, renaming with
dependents) is a rebuild:

```sql
PRAGMA foreign_keys=OFF;
CREATE TABLE `__new_user` (...);
INSERT INTO `__new_user` SELECT ... FROM `user`;
DROP TABLE `user`;                       -- runs with foreign keys ON
ALTER TABLE `__new_user` RENAME TO `user`;
PRAGMA foreign_keys=ON;
```

On D1 the `DROP TABLE` cascades: every row in `session`, `account`, `api_keys`,
`workspace`, … with `ON DELETE CASCADE` to `user` is deleted, and the rename
brings the user rows back with nothing attached. This is pinned by
`packages/db/src/__tests__/migrations.workers.test.ts` on a Miniflare D1.

Hence:

- every migration is expand/contract (above), and
- every generated file is inspected for `__new_` / `PRAGMA foreign_keys=OFF`
  before commit; `pnpm check:standards` (`no-d1-table-rebuild`) fails any file in
  `packages/db/migrations` other than the two pre-provisioning ones that
  contains either.

If drizzle-kit insists on a rebuild, do not ship it. Reshape the change: add a
new nullable column instead of altering one; add a new table and copy instead of
altering a referenced one; leave a dead column in place (rename it in the
schema with an explicit DB name and stop reading it) rather than dropping it
from a table that is a cascade target.

### Worked example: add now, drop next release

Goal: `post.author_id` replaces a `post.author_email` text column.

**Release N (expand).** Schema: add `authorId` nullable with a FK to `user`,
keep `authorEmail`. `pnpm db:generate` gives:

```sql
ALTER TABLE `post` ADD `author_id` text REFERENCES `user`(`id`) ON DELETE SET NULL;--> statement-breakpoint
CREATE INDEX `post_author_id_idx` ON `post` (`author_id`);
```

Ship it. The service writes both columns and reads `author_id ?? lookup(author_email)`.
Backfill with a one-off `wrangler d1 execute DB --remote --command "UPDATE post SET author_id = (SELECT id FROM user WHERE email = post.author_email) WHERE author_id IS NULL"`
or a follow-up migration containing only that `UPDATE`.

**Release N+1 (contract).** Once every deployed version reads `author_id`,
remove `authorEmail` from the schema. drizzle-kit emits a plain
`ALTER TABLE \`post\` DROP COLUMN \`author_email\`;` for an unconstrained
column (SQLite ≥ 3.35 supports it). If it emits a `__new_post` rebuild instead
(the column carried a constraint or index), keep the column and stop using it —
the schema can omit it; DDL and app disagree only about a column the app never
touches.

`author_id` stays nullable in DDL. Required-ness lives in the domain `Schema`.

### created_at has no database default

`created_at integer NOT NULL` with no `DEFAULT`: it is app-supplied
(`columns.ts#timestamps` → `$defaultFn(() => new Date())`; better-auth sets
`createdAt` itself). Anything that bypasses drizzle — a `wrangler d1 execute`,
the D1 console, `Database.plain` outside better-auth, a backfill `INSERT` in a
migration — must supply `created_at` (epoch milliseconds) or the insert fails.
`seed/seed.sql` pins it to a fixed `SEED_AT` for that reason.

### The issuer migration is empty-database-only

`20260903035551_auth_1_7_issuer.sql` adds `account.issuer text NOT NULL` with
no default and rebuilds `user` and `verification` with the recipe above. It was
generated before any stage database existed and is safe only on an empty one
(the Workers suite applies it from empty). It is exempt from the standards
rule for that reason and must not be used as a template; the ADR records the
finding.

## No interactive transactions

D1 has none, and `@effect/sql-d1` turns `withTransaction` into a defect (a die,
not a typed failure). The `Database` service therefore removes
`db.transaction` and offers two primitives; `pnpm check:standards`
(`no-db-transaction`) forbids the rest in `packages/{db,auth,api,domain}/src`
and `apps/web/src`.

| Need | Use | Notes |
|---|---|---|
| Several writes that must all apply or none, with no branching on an earlier result | `Database.batch([stmt, stmt, …])` | D1 `batch`: atomic, results are raw rows per statement. Delete-account cascades, invite accept (membership + allowlist), the seed. |
| Read-then-decide writes (bootstrap once, review a pending entry) | a **guarded write**: put the precondition in the `WHERE` and call `Database.updateWhere(update)` | Returns the changed-row count via `RETURNING 1`; `0` means another actor won, so the service fails with `Conflict`. |

A batch cannot look at an earlier statement's result, and a guarded write cannot
span two tables; if you need both, restructure (usually: guarded write first,
then a batch keyed on the row it claimed).

## Backups: Time Travel and export

D1 keeps a **30-day point-in-time history** (Time Travel; 7 days on the Free
plan) of every database, with no setup. Bookmarks identify a point in time.

```bash
cd packages/db
# what does the database look like at a point in time? (prints the bookmark)
pnpm exec wrangler d1 time-travel info DB --timestamp 2026-09-03T08:00:00Z --config ../../apps/web/wrangler.jsonc
# restore in place to that point (or --bookmark <id>); take an export first
pnpm exec wrangler d1 time-travel restore DB --timestamp 2026-09-03T08:00:00Z --config ../../apps/web/wrangler.jsonc
```

`restore` rewrites the live database; a bookmark of the pre-restore state is
printed so it can be undone. It also restores `d1_migrations`, so a migration
applied after the chosen point is unapplied as far as wrangler knows and will
run again on the next `apply` — check it is still safe to re-run (expand/
contract migrations are).

Exports are plain SQL and are the way to keep a copy outside Cloudflare, to
seed a local database with real data, or to move a database:

```bash
# full dump (schema + data) of the stage database
pnpm exec wrangler d1 export DB --remote --output ../../.artifacts/d1-$(date +%Y%m%dT%H%M%S).sql --config ../../apps/web/wrangler.jsonc
# data only, selected tables
pnpm exec wrangler d1 export DB --remote --no-schema --table user --table workspace --output users.sql --config ../../apps/web/wrangler.jsonc
# load an export into the local database
pnpm exec wrangler d1 execute DB --local --file users.sql --config ../../apps/web/wrangler.jsonc
```

Take an export before every `time-travel restore` and before any migration
that backfills or deletes. Procedures are in `docs/RUNBOOK.md` → "D1
operations".

## Size and scaling boundary

A D1 database is capped at **10 GB** on the Workers Paid plan (500 MB on Free),
with per-query row and duration limits on top; see Cloudflare's D1 limits page
for the current numbers. Watch `wrangler d1 info DB` (`database_size`) and plan
for a split (per-tenant databases, or moving cold tables out) well before the
cap: D1 has no online resize. This template runs a single database; read
replication (the D1 Sessions API) is off, and the `Database` service accepts an
unused `bookmark` option so read-your-writes can be added without touching
services when it is turned on.

## Tips

- `pnpm db:check` after any manual edit under `drizzle/` — the snapshots must
  stay consistent or the next `generate` diffs against the wrong state.
- `drizzle-kit generate --output json` is the non-interactive mode for agents
  and CI; `--explain` dry-runs.
- The Node test layer (`@gmacko/db/testing`) applies `migrations/*.sql` to an
  in-memory sqlite-node database and turns foreign keys on explicitly; D1 has
  them on unconditionally. If a migration passes on Node and fails on D1, run
  `pnpm -F @gmacko/db test:workers` for the D1 view.
- `pnpm auth:generate` writes better-auth's CLI output to
  `packages/db/.cache/auth-schema.generated.ts`; reconcile it into
  `auth-schema.ts` by hand (the header lists the deliberate differences, such as
  the NOT NULL `role` column). The committed file is never overwritten.
