OAuth for the remote MCP server Approved design · spike done

2026-10-30 · create-gmacko-app @ crea-6-mcp-oauth · CREA-6

Decision: Serve a Streamable HTTP /mcp endpoint from the Worker, protected by better-auth's OAuth 2.1 provider. On a consent page the user pins the grant to one workspace and picks resource:action scopes. That scope vocabulary replaces read/write/delete/admin for API keys too, so each credential type is checked against the same catalog.

Decisions taken

Host

Remote /mcp in apps/web. The stdio gmacko-mcp server and its API-key auth stay unchanged for local use and CI.

Workspace

One workspace per grant. It replaces resolveWorkspace for that token. If the membership is lost, the token gets a 401.

Scopes

A new resource:action catalog, unified: API keys migrate to it.

Auth server

@better-auth/oauth-provider 1.7.14 (better-auth bumped from 1.7.2): DCR, PKCE, and RFC 8707 resources, with opaque tokens in D1 next to sessions.

Goals and non-goals

In scope

  • MCP-spec discovery: protected-resource and AS metadata, 401 with WWW-Authenticate
  • Consent page with a workspace picker and grouped scopes
  • One scope catalog for sessions, keys, and OAuth tokens
  • tools/list filtered by the granted scopes
  • "Connected apps" in Settings: list and revoke
  • Template scaffolding emits all of it

Out of scope

  • Multiple workspaces per grant
  • Changing scopes without re-consent
  • admin or api_keys:manage over OAuth
  • Verified-publisher client allowlists
  • OAuth for the stdio server

Architecture

Every authenticated request resolves to a principal: user, workspace, and scopes. The three credential types differ only in where those values come from.

packages/domain

scopes.ts catalog with a grantable flag; RequireScope(scope) replaces SessionOrKey(level).

packages/auth

oauthProvider({ postLogin, consentPage, resources, disableJwtPlugin: true }). The bearer scheme verifies gmk_ keys and OAuth tokens, and RequestContext.workspace honours the pin.

apps/web

/oauth/workspace (post-login picker) and /oauth/consent routes, /.well-known/*, and /mcp, which reuses @gmacko/operator-core through its in-process transport with the bearer forwarded.

packages/db

The plugin's tables (client, resource, consent, access/refresh token), a nullable session.oauth_workspace_id, and an api_keys.permissions data migration. No custom grant table.

Connect flow

  1. DiscoverPOST /mcp returns 401 with resource_metadata
  2. RegisterThe client self-registers (DCR)
  3. AuthorizePKCE and resource=…/mcp; sign in if needed
  4. WorkspaceThe postLogin page stores the pick on the session, then /oauth2/continue
  5. ConsentPick scopes (subset allowed); consentReferenceId returns the workspace; DCR clients are marked "unverified"
  6. TokenCode exchanged; audience bound to /mcp

A user with no workspace sees "you need a workspace" and cannot approve. Deny returns access_denied.

Mitigations

R1, gaps in the plugin API: resolved. 1.7.14 covers all three requirements: consentPage with a scope subset at /oauth2/consent; resources with per-resource allowedScopes and invalid_target enforcement; and postLogin.consentReferenceId, documented for "selection of an organization or team". This was confirmed by reading the source, not run end to end; phase 2's workers test is the runtime proof.

R5, two simultaneous authorize flows in one browser session share session.oauth_workspace_id. The later pick wins. The consent page names the workspace being granted, and the plugin's shouldRedirect re-validates membership on continuation.

R2, the key migration widens or narrows access. The expansion is cumulative and table-tested, and the old column value is logged before rewriting.

R3, the MCP SDK's Streamable HTTP transport assumes Node. Use its Web-standard transport or a thin fetch adapter, and test under workerd.

R4, anyone can register clients through DCR. Consent marks DCR clients as unverified and shows the redirect host. Registration goes through RateLimit, and admin scopes are never grantable.

Verification

Acceptance criteria are on CREA-6. Each PR must pass pnpm check:fast, check:standards, and the workers tests. The final one adds an MCP Inspector run through DCR, sign-in, consent, and token against local dev.

Open questions

None blocking. The spike replaced the custom oauth_grant_workspace table with the plugin's referenceId, and chose opaque tokens (no JWKS keys to manage, immediate revocation) because /mcp verifies in the same Worker as the authorization server.
